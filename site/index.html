        It sees the exit's address

      1. Your client sends the exit a fresh random number and asks for its Intel quote.
      2. It checks Intel's signature, that debug is off, and that the quote contains the exit's keys and your number.
      3. It reads the NEAR registry: is this build allowed, is this OS allowed, is this exit registered.
      4. Only then it opens an encrypted tunnel to the key in the quote. If the owner revokes the build, the next connection is refused.

      Check the exit from your own machine

      Node 22 and a network connection. No accounts.

      Verify the live exit and send one request through it

      npm ci && npx tsc -b && scripts/try-live.sh

      Prints every check, starts a local SOCKS5 proxy on 127.0.0.1:18180, and shows your IP next to the IP a website sees through the exit. It changes no system settings and needs no sudo.

      Replay the recorded check without a network

      npm ci && npx tsc -b && node client/dist/cli.js vpn verify --fixture fixtures/live-exit

      Replays the same exit's quote and registry state from a capture. You see one ✔ line for each check and ✔ VERIFIED (FIXTURE REPLAY …).

      An MCP server for AI agents

      Your agent checks the exit, then fetches pages through it. If any check fails, it fetches nothing and returns the error code.

      verify_exit
      Runs the same checks as this page and returns the verdict and each check.
      fetch_via_exit
      Gets an http or https URL on port 80 or 443 through the verified tunnel. The exit resolves the hostname.
      registry_status
      Returns the NEAR registry: owner, code hash, key count, history.

      Add it to Claude Code

      claude mcp add provenexit -- node /path/to/provenexit-mcp.mjs

      One file, Node 22, runs on your machine. It is in the repo at mcp/dist/provenexit-mcp.mjs.

      Claude Desktop, in claude_desktop_config.json

      { "mcpServers": { "provenexit": { "command": "node", "args": ["/path/to/provenexit-mcp.mjs"] } } }

      Only what goes through fetch_via_exit uses the exit. The agent's model calls and its other tools do not.

      What this does not prove

      1. Testnet only.

        The registry is on NEAR testnet.

      2. The exit sees your destinations.

        Any VPN exit must know the host and port it connects to. ProvenExit proves the approved code does not keep them, not that it never sees them. TLS hides the content, not the host.

      3. Timing and metadata are visible to the operator's network.

        “No logs” covers the attested code, not the operator's host, which can observe destination IP and port, timing, the TLS SNI and every byte of plain HTTP. Traffic is not padded. With one hop, your IP is visible to the exit operator's network.

      4. Intel and the dstack OS are trusted.

        Intel, the dstack OS image and the TDX module are trusted roots. Side channels are not defended.

      5. One owner key decides the allowlist.

        The owner is one NEAR account. Whoever holds that key can allow or revoke builds and operators. Multisig is future work.

      Also true

      1. Proxy only: TCP through a SOCKS5 proxy. No UDP, no QUIC, no system-wide tunnel.

      2. The NEAR RPC endpoint is trusted: view results carry no state proofs.

      3. Phala's gateway terminates TLS in front of the exit. It sees only tunnel ciphertext, can observe timing and volume, and can refuse to serve.

      4. The OS measurement was observed in the quote, not rebuilt from source.

      5. The exit image is not reproducible yet: a rebuild is not shown to give the same digest.

      6. An exit can serve Intel revocation data that is stale but not expired; the window is the list's update interval.

      7. The exit is paid by the hour. It runs through judging and may be stopped afterwards.
